02 · modelo mental

Captain conversa, consulta conocimiento y propone solo acciones configuradas.

Mensaje
→
Assistant + reglas
→
Escenario
si coincide
→
Respuesta, tool o handoff

Diseño correcto

  • Conocimiento revisado antes de automatizar.
  • Tools pequeñas y con propósito explícito.
  • Handoff cuando faltan datos, permiso o certeza.

No asumir

  • Que una tool autoriza una acción por sí misma.
  • Que el assistant puede inventar una integración.
  • Que los escenarios resuelven ambigüedades por prioridad persistida.

03 · antes de configurar

Habilita la capacidad y prepara una ruta de atención humana.

Cuenta y permisos

  • Captain y el proveedor/modelo deben estar disponibles para la cuenta.
  • Para MCP externo, habilita captain_mcp.
  • Crear/editar assistants, escenarios, Custom Tools y MCP requiere administrador.
  • Los agentes pueden consultar el assistant y usar Playground, sin administrar esas configuraciones.

Operación

  • Define objetivo, owner de contenido y criterio de escalación.
  • Prepara el inbox piloto, pero no asignes el assistant todavía.
  • Pide al administrador de instancia confirmar el modo de cuenta disabled para auto-resolve.
  • Prepara casos normal, límite y handoff para probar.
⚠Exclusividad de bots: Captain no responde ni programa resoluciones automáticas en inboxes con Agent Bot activo o Dialogflow.

Completa el alcance y los mensajes antes de asignar el primer inbox.

Ejemplo de alcance

Mensajes sugeridos

07 · contexto y alcance

El conocimiento confiable viene antes de la acción.

FAQs

Aprueba solo respuestas reutilizables; revisa las sugerencias antes de publicarlas.

Documents

URL pública o PDF relevante. Un PDF tiene máximo 10 MB y se procesa/indexa.

Inboxes

Selecciona un canal piloto sin bots en conflicto y asígnalo solo después de Playground.

🔎Citas: usa URLs públicas y aptas para el cliente. No cites URLs con credenciales, parámetros firmados, PDFs ni destinos privados.

08 · comportamiento seguro

Separa estilo, prohibiciones y resolución automática.

Response guidelines

Cómo responder: idioma, tono, estructura, preguntas de aclaración y cuándo ofrecer ayuda humana.

“Responde en español, en pasos cortos.”

Guardrails

Qué no hacer: promesas, PII sensible, decisiones reguladas o acciones sin confirmar.

“No solicites ni repitas datos de tarjeta.”

Disabled

Sin resolución automática. Recomendado para el lanzamiento.

Evaluated

Con captain_tasks: resuelve si está completa; hace handoff si está incompleta.

Legacy

Cierre por tiempo de inactividad; úsalo solo si el equipo conoce ese comportamiento.

Configuración de cuenta: no existe selector en la UI actual de Captain. El administrador de instancia debe verificar captain_auto_resolve_mode; sin valor explícito, el fallback depende de captain_tasks.

09 · especializar sin solapar

Un escenario es un agente especializado para una intención precisa.

Campos visibles

  1. Title: la intención, no la solución.
  2. Description: señales de entrada y exclusiones.
  3. Instruction: pasos cortos y verificables.
  4. Tool links: se insertan desde el selector dentro del editor.

Activación real

Un escenario nuevo se crea habilitado por defecto y la UI actual no ofrece un interruptor.

No hay prioridad persistida: haz escenarios mutuamente excluyentes y configura antes de asignar el inbox.

✓No existe un campo Tools separado en la UI: el sistema infiere las tools desde enlaces tool:// de la instrucción y rechaza referencias no configuradas.

10 · primer caso copiable

Un escenario también puede responder sin ejecutar ninguna tool.

Campos exactos

TitleHorarios de atención
DescriptionConsultas sobre horarios, canales y cobertura; no gestiona casos.
InstructionTexto del ejemplo, sin insertar enlaces tool://.

Al crear: queda habilitado. Hazlo antes de asignar el inbox piloto.

Instruction
Si la persona pregunta por horarios, canales o cobertura:
1. Responde solo con conocimiento aprobado.
2. No ejecutes acciones ni prometas seguimiento.
3. Si el pedido está fuera de este alcance,
   vuelve al assistant principal.
✓Resultado esperado: no hay tool chain. El escenario da una respuesta acotada y el assistant principal retoma las intenciones fuera de alcance.

↗Handoff no asigna automáticamente equipo, prioridad ni tiempo de respuesta. Úsalo cuando la persona lo pide/acepta, salvo que una guideline o guardrail exija escalación.

12 · integración por cuenta

Define un contrato pequeño, seguro y verificable antes de usarlo en un escenario.

Custom Tool ficticia

Title / IDConsultar estado pedido · custom_consultar_estado_pedido esperado sin colisión.
DescriptionConsulta por order_id el estado publicado de un pedido; solo lectura.
HTTP methodGET
Endpoint URLhttps://api.ejemplo.test/v1/orders/{{ order_id }}
AuthBearer · valor ficticio demo-no-usar
Parameterorder_id · string · required · identificador público.

Respuesta mínima al modelo

Response template
Estado: {{ response.status }}
Fecha estimada: {{ response.estimated_date }}
# No devolver dirección, teléfono ni datos de pago.

Test: está deshabilitado porque la URL tiene {{ ... }}.

Privacidad: cada llamada agrega headers de cuenta/assistant y, si existen, conversación, contacto, email y teléfono. Autoriza el endpoint como receptor de datos personales.

⚠Mantén idealmente 10 o menos para facilitar la selección; el máximo es 15 por cuenta. Persistir exige HTTPS público; no localhost, IP, .local ni la propia app. Guarda secretos solo en Auth y usa el ID que inserta el selector. Una mutación requiere confirmación propia.

13 · integración por assistant

Conecta, descubre y filtra las tools del servidor remoto antes de asignarlo.

NameInventario Demo
DescriptionConsulta disponibilidad de productos; solo lectura.
URLhttps://mcp.ejemplo.test/mcp
Transport / RPCstreamable_http · RPC endpoint vacío.
Auth typeBearer · token ficticio
Enabled✓

Adjuntar al assistant

  1. Selecciona Inventario Demo.
  2. Tras Connect, elige solo stock_lookup.
  3. ID esperado sin colisión: mcp_inventario_demo_stock_lookup.
  4. Inserta la tool desde el selector del escenario; no escribas el ID de memoria.
  5. Servidor + asociación habilitados y estado connected.

↻Import Configuration acepta JSON remoto y rechaza stdio. Para cambios inmediatos usa Connect/Refresh; el job revisa cada 10 minutos y la renovación efectiva puede acercarse a 20 minutos más cola.

14 · construir de afuera hacia adentro

El orden de configuración determina qué tools puede usar el escenario.

1Crear/habilitar custom_consultar_estado_pedido con permisos de solo lectura.Cuenta
2Conectar Inventario Demo, adjuntarlo al assistant y filtrar stock_lookup.Assistant
3Verificar que los built-ins necesarios estén configurados y disponibles.Catálogo
4Crear el escenario —queda habilitado—, probarlo y recién después asignar el inbox.Escenario

Permitido

Estado de pedido, stock, nota privada, prioridad y handoff: todos definidos con identificadores concretos.

Bloqueado / fallback

Si falta order_id, una tool falla o no se confirma el retraso: no mutar; pedir el dato u ofrecer handoff y ejecutarlo solo si acepta.

15 · escenario copiable

Pedido con posible retraso: consulta, registra y escala de forma condicional.

Title: Pedido con posible retraso
Description: Consulta estado y stock cuando un pedido puede retrasarse.

Instruction
Si la persona consulta un pedido con posible retraso:
1. Pide order_id si falta. Si no lo aporta, ve al fallback del paso 7.
2. Usa [Consultar estado](tool://custom_consultar_estado_pedido).
   Si falla o no confirma el estado, ve al fallback del paso 7.
3. Solo si el estado requiere reposición, usa
   [Consultar stock](tool://mcp_inventario_demo_stock_lookup).
   Si no está disponible o falla, ve al fallback del paso 7.
4. Solo con retraso confirmado, registra el resultado con
   [Añadir nota privada](tool://add_private_note).
5. Solo si el retraso está confirmado, usa
   [Actualizar prioridad](tool://update_priority) con high.
6. Explica únicamente resultados confirmados.
7. Fallback: ofrece ayuda humana. Si acepta, usa
   [Transferir a humano](tool://handoff); si no, finaliza sin más tools.
8. Si la intención no es un pedido, vuelve al assistant principal.

Nota: los IDs son los esperados en una cuenta demo sin colisiones. Inserta cada referencia desde el selector del editor. El runtime admite hasta 128 tools; un escenario permite asignar hasta 127.

16 · cómo demostrarlo

La traza muestra que una configuración no reemplaza la autorización.

1Cliente: “¿Qué pasa con el pedido ORD-DEMO-1042?”Entrada
2Custom Tool GET devuelve delayed; el endpoint ya fue autorizado para metadata.Lectura
3MCP stock_lookup confirma reposición disponible.MCP
4En inbox piloto: nota privada y prioridad high solo con retraso confirmado.Interno
5La persona acepta ayuda humana → handoff con motivo. Sin aceptación, no transferir.Humano
✓Dos pruebas: Playground muestra routing y trazas, pero no tiene conversación real; nota, prioridad y handoff humano se validan en el inbox piloto. En V2 no hay selector directo @ en Playground.

17 · dos direcciones distintas

Distingue quién consume MCP y qué autenticación corresponde.

Captain consume MCP externo

Se configura un servidor remoto HTTP(S), con auth none/Bearer/API key, se conecta y se filtran tools por assistant.

Ejemplo: Inventario Demo

Cliente IA consume MCP nativo

Un cliente se conecta al endpoint de cuenta /mcp/:account_id/:slug con OAuth o API access token y el catálogo permitido.

No publica importación/exportación

🔐Una ejecución de Captain hacia MCP nativo incluye prueba firmada, de un solo uso y ligada a cuenta, assistant, servidor, endpoint, tool y argumentos. Sigue siendo necesario aplicar mínimo privilegio.

19 · validar antes de exponer

Playground valida decisiones; el inbox piloto valida el contexto operacional.

En Playground

  1. Pregunta cubierta por FAQ/documento.
  2. Escenario simple sin tools.
  3. Routing del caso complejo y tools externas.
  4. Dato faltante y tool desconectada.
  5. Trazas de tools y handoffs entre agentes en V2.

En inbox piloto

  1. Modo de cuenta disabled confirmado.
  2. Recién ahora asignar un canal, horario y owner.
  3. Validar notas, prioridad y handoff humano.
  4. Medir reaperturas y consultas no resueltas.
  5. Ampliar solo con evidencia estable.
◌Playground usa la configuración real, pero no crea una conversación: las tools ligadas a conversación no producen allí sus efectos finales. Valídalas en el inbox piloto.

20 · diagnosticar sin adivinar

Corrige la configuración que limita el flujo; no agregues instrucciones para ocultar el problema.

Test de Custom Tool deshabilitado

Causa: URL con {{ ... }} o request template.

Acción: con POST/PUT/PATCH vacía primero Request template; luego usa una URL estática GET segura, o crea una tool temporal. Test ejecuta una llamada real.

MCP tool no aparece

Causa: servidor desconectado/deshabilitado o tool no seleccionada en la asociación.

Acción: Connect/Refresh, comprueba estado connected, enabled y filtro include/exclude.

Escenario equivocado

Causa: descripciones o señales solapadas.

Acción: estrecha la intención y añade exclusiones; no hay prioridad persistida que lo arregle.

Endpoint inseguro o error de red

Causa: HTTP no seguro para Custom Tool, host privado/local o DNS a IP privada.

Acción: usa HTTPS público y revisa timeout/respuesta; no intentes sortear las protecciones SSRF.

21 · operar con evidencia

El primer lanzamiento es un experimento controlado, no el final del diseño.

Overview

Atendidas, resolución automática, handoffs, reaperturas, cobertura y tiempo ahorrado estimado.

Detalles de generación

Inspecciona escenarios, tools y fuentes de respuestas/notas Captain para auditar decisiones.

Rutina semanal

Corregir FAQs, retirar tools inútiles, revisar errores y repetir los mismos casos de Playground.

  • Assistant, fuentes e inbox piloto revisados.
  • Sin Agent Bot/Dialogflow en el inbox.
  • Guidelines, guardrails y auto-resolve definidos.
  • Escenarios no solapados; salida segura clara.
  • Custom/MCP con mínimo privilegio y sin secretos reales.
  • Máximo 128 en runtime, 127 por escenario y 15 Custom Tools.
  • Casos normal, límite y handoff aprobados.
  • Owner, monitoreo y reversión definidos.

Cierre

Empieza estrecho.
Mide. Aprende.
Amplía con cuidado.

Captain funciona mejor con conocimiento confiable, decisiones explícitas y tools de alcance pequeño.
